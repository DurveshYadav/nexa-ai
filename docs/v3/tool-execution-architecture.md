# NexaAI V3 — Tool Execution Architecture

## 1. Objective

Define a secure and controlled architecture for executing
LLM-requested business tools.

## 2. Tool Execution Components

### Tool Definition
Contains:
- Tool name.
- Description.
- Input schema.
- Permission requirements.
- Approval requirements.

### Tool Registry
- Stores approved tool definitions.
- Provides lookup by tool name.
- Exposes tool schemas to the LLM.
- Does not execute tools.

### Tool Executor
- Receives tool calls from Orchestrator.
- Looks up registered tools.
- Validates arguments.
- Checks authorization.
- Checks approval requirements.
- Dispatches handlers.
- Normalizes results and errors.
- Records execution audit information.

### Tool Handler
- Receives validated arguments and trusted context.
- Delegates to the appropriate Business Service.
- Returns structured results.

### Business Service
- Applies business rules.
- Checks resource ownership and operation constraints.
- Uses repositories or external integrations.
- Returns operation results.

## 3. Execution Sequence

1. Orchestrator receives an LLM tool call.
2. Tool Executor extracts the tool name and arguments.
3. Registry lookup verifies that the tool exists.
4. Pydantic validates the arguments.
5. Backend Execution Context supplies trusted identity.
6. Authorization checks verify permissions and resource ownership.
7. Approval requirements are evaluated.
8. Approved handler is dispatched.
9. Business Service performs the operation.
10. Executor normalizes the result.
11. Audit information is recorded.
12. Orchestrator receives the result.

## 5. Trusted Identity

Never trust user_id or customer_id supplied by the LLM.

Use:
- user_id from authenticated backend context.
- conversation_id verified by Agent Service.
- run_id generated by backend.
- permissions determined by backend authorization.

Resource ownership must be checked before accessing or modifying
customer-specific data.

## 6. Argument Validation

Every tool must define a strict input schema.

Validation must reject:
- Missing required fields.
- Unexpected fields where strict validation is configured.
- Invalid data types.
- Invalid identifiers.
- Values outside business constraints.

Invalid arguments must never reach Business Services.

## 7. Authorization and Approval

Authorization answers:
"Is this user allowed to perform this operation?"

Approval answers:
"Has the required confirmation been provided?"

These are separate checks.

Sensitive operations must not execute before required approval.
Approval must be associated with the intended operation and its
validated parameters.

Recheck authorization and business conditions before execution.

## 8. Normalized Tool Results

Successful result:

{
  "success": true,
  "tool_name": "get_order_status",
  "data": {
    "status": "shipped"
  },
  "error": null
}

Failed result:

{
  "success": false,
  "tool_name": "get_order_status",
  "data": null,
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "Order not found."
  }
}

Do not expose internal exception details or secrets to the LLM.

## 9. Audit Information

Record relevant execution metadata:
- run_id.
- request_id.
- authenticated user_id.
- tool name.
- execution status.
- timestamp.
- duration.
- approval reference when applicable.

Do not log passwords, API keys, raw tokens, or unnecessary
sensitive customer information.

## 10. Failure Handling

- Unknown tool: reject execution.
- Invalid arguments: return validation failure.
- Unauthorized operation: reject execution.
- Approval missing: pause execution.
- Business rule violation: return structured failure.
- External API failure: return controlled failure.
- Unexpected exception: log safely and return generic failure.

A failed operation must never be represented as successful.

## 11. Security Principles

- Allowlist tools through Tool Registry.
- Validate every tool argument.
- Use backend-owned Execution Context.
- Enforce resource-level authorization.
- Require approval for sensitive operations.
- Apply execution limits and timeouts.
- Maintain audit records.
- Never allow the LLM direct database access.

## 12. Key Principle

The LLM proposes a tool call.
The Registry identifies approved tools.
The Executor validates and authorizes execution.
The Business Service enforces business rules.
The backend records and returns the actual result.
